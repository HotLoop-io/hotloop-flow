HotLoop Flow 2.10.2 is 2.10.0 with the arm64 image added, which is what 2.10.1 was meant to be. 2.10.1's chart was published but its image never was: the release run stopped at the registry login, so there is no 2.10.1 image to pull. Use 2.10.2. There is no change to the code, the chart, the settings or your flows.

## What changed

- The image is built for linux/amd64 and linux/arm64. The `2.10.2`, `2.10` and `2` tags hold both.
- The release run no longer breaks its own registry login. Registering arm64 emulation runs Podman as root, and root's Podman wrote its login into the runner user's runtime folder, owned by root, so the user's own login after it was refused. Root now keeps its login in its own place (`build/mirror-image.sh` and the arm64 step in `image-publish.yml`).
- The README and the install pages name 2.10.2.

## New settings

None.

## Upgrade

A plain `helm upgrade` to the 2.10.2 image and chart, or the new tag in your Quadlet unit. From 2.10.0 nothing changes on amd64. If you are on arm64 and still on 2.9.1, this is your move to everything in the 2.10.0 notes: FlowLab's instruments, case structure, waveforms, shared record types, sub-diagrams and log rotation, the MCP tools that list, read, deploy and roll back flows, the heap held to the container's memory limit, and the fix that stops a durable MQTT output sending a message twice after a reconnect. Nothing happens on first start and nothing needs migrating. If anything pinned 2.10.1, move it to 2.10.2: that image does not exist.

## What isn't proven

The arm64 image is built under emulation on the runner, and it starts and reports its version in the release run. It has not been run on an arm64 box for this release.

Image: `ghcr.io/hotloop-io/hotloop-flow:2.10.2`, linux/amd64 and linux/arm64. Chart: `https://hotloop.io/hotloop-flow/`. The README at this tag has the rest, with pictures: https://github.com/HotLoop-io/hotloop-flow/blob/v2.10.2/README.md
