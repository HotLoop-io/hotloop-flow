HotLoop Flow 2.16.0 lets one flow file, and so one set of FlowLab diagrams, be pushed to every Flow install a tenant runs in EmberNet, with a check after each one, and a failed one put back. It is amd64 first, with arm64 following in 2.16.1.

## What's new

- **Push to a tenant's stations (#201).** `hotloop-flow stations list -tenant ID` and `hotloop-flow stations push -tenant ID -file flows.json` put one flow file on each Flow install EmberNet shows as running for the tenant, one at a time. The stations come from the EmberNet dashboard and are never typed in, and a row of any other tenant is dropped. After each deploy the station must answer the revision every station is to have, have no node that failed to start, and have every diagram of the file that starts by itself present and running or finished. A station that fails is rolled back to the deployment it was on and the push stops; the report says which stations were done, failed, skipped and never started. A push that would restart a running logger changes nothing until the operator says yes at the prompt, passes `-confirm-restart`, or gives a `-window` that holds now. `docs/stations.md` is the page.
- **The same push over the API and MCP (#201).** `GET /stations` and `POST /stations/push`, and the MCP tools `list_stations` and `push_to_stations`, which brings the tools to 43. They are there only where the four stations settings are set.
- **Chart values and Quadlet lines (#202).** `stations.dashboardUrl`, `stations.tenant`, `stations.dashboardTokenSecret` and `stations.deployTokenSecret` in the chart, with the two Secrets mounted as files, and the four environment variables and two mounted secrets for a Quadlet unit in `docs/deploying.md`. CI now renders the chart with none, some and all of them.

## What changed

- A start with only some of the four stations settings is refused, and so is a chart render with some of them. All four or none.
- A token that pushes to stations needs `status.read` as well as `flows.read` and `flows.write`, because the check after each deploy reads the station's diagrams. `hotloop-flow token` now prints that, and so do the README and the stations page. A plain deploy token still works for `deploy` as before.
- The revision a flow set will have once saved can now be known before it is saved, from one function the save also uses. Nothing about revisions changed.
- The docs name `hotloop-flow-mcp-server` where they said `mcp-server` (#197, #199, #200).
- The static binary is 51,859,618 bytes (49 MiB), under the 50 MiB budget in `ci.yml`.

## New settings

`stations.dashboardUrl`, `stations.tenant`, `stations.dashboardTokenFile` and `stations.deployTokenFile` in the config file, or `HOTLOOP_FLOW_STATIONS_DASHBOARD_URL`, `HOTLOOP_FLOW_STATIONS_TENANT`, `HOTLOOP_FLOW_STATIONS_DASHBOARD_TOKEN_FILE` and `HOTLOOP_FLOW_STATIONS_DEPLOY_TOKEN_FILE`. All empty by default, which leaves the feature off. In the chart they are the `stations.*` values above.

## Upgrade

A plain `helm upgrade` to the 2.16.0 image and chart, or the new tag in your Quadlet unit. Nothing happens on first start and nothing needs migrating. A flow file loads and saves byte for byte as before. This release is amd64 only: arm64 boxes stay on 2.15.1 until 2.16.1, which is the same code with the arm64 image added.

## What isn't proven

The push was run against three real Flow instances in tests and as three real processes on a lab box, one of them Flow 2.6.0, with a stand-in for the dashboard that served the real shape of its list. It has not been pushed through Flux to a real tenant's stations, and the real dashboard's answer on this code has not been read. A station with no deployment record of its live revision is skipped, because a failed push could not be undone there: deploy to it once first. The chart values and the Quadlet lines were rendered and checked in CI and not run on a cluster or a box. The command, the API and the page are in English only.
