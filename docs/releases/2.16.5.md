HotLoop Flow 2.16.5 stops a Modbus read from stacking up behind a device that answers slower than it is asked. Nothing in your flows, settings or chart changes.

## What changed

- **A poll asked again while the last is still being answered is merged into the newest.** A Modbus getter, flex getter or read node polled through a connection shared with other nodes, to a PLC that answers one request at a time, was asked more than the device could answer. The node's inbox grew until it was full, and the nodes in front of it blocked and then dropped on the 30 second limit. On the plant's pod 190,000 of 320,000 queued messages sat in getters, 179 getters had a full inbox, and memory climbed with the backlog. A node can now say which of its queued messages ask the same thing, and when it takes its next message only the newest of each is handled. The getter, flex getter and read nodes key on function code, unit id, address and quantity, so a flex getter that sends different addresses still answers every different one. What comes out is the same message it always was, from the newest poll.
- **Writes are never merged.** Every write has to reach the device, in order, so the write nodes do not take part.
- **A new metric counts it.** `hotloop_flow_node_messages_coalesced_total` is the number of queued messages merged into a newer one, for each node.

## What it fixes, with numbers

A device that takes 40 ms to answer, asked 100 times a second by one getter, over 6 seconds on one machine:

| | 2.16.4 | 2.16.5 |
|---|---|---|
| Polls stacked in the inbox | 377 and growing | 1 |
| Polls answered | 123 | 123 |
| Polls merged | 0 | 376 |

## New settings

None.

## Upgrade

A plain `helm upgrade` to the 2.16.5 image and chart, or the new tag in your Quadlet unit. Nothing happens on first start and nothing needs migrating. A flow file loads and saves byte for byte as before. This release builds the amd64 image. The `2.16` and `2` tags keep the arm64 image they already hold from 2.16.1, and arm64 comes back in 2.16.6. If you are on arm64, stay on 2.16.1 until then.

## What isn't proven

The numbers are from a synthetic device, not the plant's. A getter's output now answers the newest poll and not every poll, so a flow that counts getter replies as a clock sees fewer of them when the device is the slow part. Write nodes still queue: on the plant 57 flex write inboxes were full behind the same slow connections, and merging writes can lose a pulse, so that needs its own decision. On the plant's pod, at 4.3 KB of memory for each queued message, the queue that remains would stay under the 4 Gi limit if only the nodes that queue today fill.
