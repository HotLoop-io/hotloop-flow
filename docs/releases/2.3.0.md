HotLoop Flow 2.3.0 is the release where Flow talks to HotLoop, and where the `json` node learns to check a value against a JSON Schema. Flow reads what HotLoop knows, runs its scripts, applies its recipes, and can send an equipment write through HotLoop's write gate instead of straight to the PLC. One change can affect a flow that already runs, and it is the first thing under What changed.

## What's new

**A schema on the `json` node**
- Give the `json` node a JSON Schema in its settings and every value it handles is checked against it. A value that matches goes on. One that doesn't goes to a Catch node instead of down the wire, and the error names every bad field, like `payload.temp: got string, want number; payload.id: missing property "id"`. `msg.schemaError` carries the same list as `{path, keyword, message}` objects for a Catch node that wants to route on it.
- With no schema in the settings, the node validates against `msg.schema`, the way Node-RED's `json` node does. A message that passes has `msg.schema` removed, and one that fails keeps it. The schema in the settings wins when both are there.
- It is JSON Schema draft 2020-12 unless the schema names another draft with `$schema`. Drafts 4, 6, 7 and 2019-09 are accepted. A schema is self-contained: a `$ref` to another URL or a file is refused, not fetched, so an edge box with no route out behaves like any other.


**HotLoop nodes**
- A `hotloop-flow-hotloop` connection, which is a URL and an account. It signs in with `POST /api/auth/login`, sends the bearer token HotLoop hands back, and signs in again when HotLoop says the session is gone. An operator account is enough for everything below.
- `hotloop in` follows HotLoop's live feed and sends a message for each entity that changes state: `msg.topic` is the entity id, `msg.payload` is the new state, and `msg.hotloop` carries the state it had before, its attributes, its quality and its timestamps. It follows the entity ids and patterns you list. If the link drops, the badge goes red and one error reaches a Catch node for the outage, not one per retry. When it comes back, an entity that changed in the meantime is sent and one that didn't isn't.
- `hotloop state` reads one entity when a message arrives.
- `hotloop script` runs a HotLoop script with the fields you give it. `hotloop recipe` applies a recipe with its parameters, and an older version if you ask for one on purpose. HotLoop checks every field and parameter, runs every write through its write gate and keeps the record. Flow sends the reason `flow:<node id>`, and HotLoop records it in its write audit and its logbook.
- A refused or failed call arrives at a Catch node with HotLoop's own words and its status: a script that is busy, a field out of range, a run that failed at step 2, a recipe refused whole because one target isn't armed. Nothing that was written is undone, because that is HotLoop's rule too.

**Writes through HotLoop's gate**
- `modbus write`, `opcua write`, `s7 write` and `ethernetip write` have two new fields, **Write through HotLoop** and **HotLoop tag** (`device/tag`). With a HotLoop picked, the value goes to HotLoop's write gate, which decides in its order: writes switched on, the tag armed, the value in range.
- A write the gate refuses never reaches the equipment. A HotLoop that can't be reached fails the write too. It never falls back to writing directly, because that would be a write the gate never saw.
- HotLoop's own address, data type and scale for the tag apply, so the address and data type on the Flow node aren't used. The node's equipment connection stays picked, and clearing the HotLoop puts the node back exactly as it was.
- The gate takes one bool, number or text per write, so a list of registers is refused with a message that says so.

That is five more node types, 75 in all.

## What changed

- The `json` node used to ignore `msg.schema`. Now a message that carries `msg.schema` is validated against it and, if it doesn't match, goes to a Catch node and not down the wire. A flow that happens to leave a `msg.schema` on its messages, for some other purpose, will see that. A flow with no schema anywhere behaves exactly as it did before.
- The validator is not Ajv. It refuses a `$ref` to anything outside the schema, and it ignores `format` values it doesn't know. It is a new Go module, `santhosh-tekuri/jsonschema` v6 (Apache-2.0), so the license text the image carries in `/usr/share/doc/hotloop-flow/` has one more entry.
- The write nodes carry the two new fields, empty by default. With no HotLoop picked, a write node behaves as it did in 2.2.0.
- A flow that never picks a HotLoop never makes a call to one.
- The README and `docs/bench/` carry the Raspberry Pi 5 results, and the roadmap now checks off the Pi 5 and leaves the Pi 4, the Zero 2 W and the SD card writes open.
- The README's node counts now match the generated matrix, and the text about HotLoop no longer says IoT and Edge are coming. All four are published as 4.18.10.

## Upgrade notes

From 2.2.0 it's a plain image bump (`helm upgrade`, or the new tag in your Quadlet unit). No migration, no flag, nothing new on first start. A `flows.json` and a config file that ran on 2.2.0 run on 2.3.0, and the byte-exact round trip of the flow file is untouched.

- Going back to 2.2.0 is safe for any flow that doesn't use the new nodes. A HotLoop node fails to start on 2.2.0 (unknown node type), and a write node with a HotLoop picked writes straight to its equipment there, because 2.2.0 doesn't read the field. Take the HotLoop off those write nodes before you go back.
- HotLoop records the account Flow signs in as. The API gives a client no way to name its own actor, so the Flow node id goes in as the reason and the account is the one on the connection. Use an account made for Flow if you want its writes easy to find.

## New settings

None in the YAML, the environment or the chart. The HotLoop connection is set in the editor: URL, username, password (kept with the other credentials) and a timeout in seconds, 15 by default. The chart has nothing new in `values.yaml`.

## What isn't proven

It has never run on a real plant floor.

- HotLoop is tested against the real thing: the published HotLoop IoT 4.18.10 image runs in CI with a login and writes on, next to the Modbus server. A write through the gate lands in the register. A write outside the tag's range, one to a tag that isn't armed, one to a tag HotLoop doesn't have, and one with HotLoop unreachable all fail with the gate's words and leave the register where it was. Scripts, recipes, `hotloop state` and `hotloop in` ran against it too, and HotLoop's write audit and logbook were checked for the account and the reason.
- The reconnect and the diffing of the live feed are tested against a small stand-in for HotLoop that answers in the documented shapes, because dropping a real HotLoop's connection on cue isn't something I can do.
- Only the Modbus write was checked through the real gate against a PLC simulator. The OPC UA, S7 and EtherNet/IP write nodes carry the same two fields and send through the same code, and a test checks each one offers the gate, but none of them was run through a real gate in CI.
- The connection trusts the system's certificate roots and nothing else, so an `https` HotLoop with a private CA isn't covered.
- No node calls a HotLoop service directly, like `switch.turn_on`. A script or a recipe does that, with HotLoop's checks.
- Everything from 2.2.0 that wasn't proven is still not proven: the S7 and EtherNet/IP nodes have only met simulators.
- Flow now has numbers from a real Raspberry Pi 5, measured on 2026-10-22 and published in `docs/bench/`: start time, memory, and throughput, run on the 2.2.0 arm64 image. The board throttled under a ten minute load, and the page says how much. A Pi 4, a Zero 2 W, and SD card writes per hour on a card are still not measured, and the roadmap says so.
